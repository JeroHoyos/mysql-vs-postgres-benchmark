\subsection{Consulta 1}

Devuelve los pokémon cuyo tipo principal es fuego, junto con el nombre y la
velocidad de su especie y el nombre del entrenador que los posee. Para ello combina
las tablas pokemon, especie y entrenador mediante JOIN.

\begin{lstlisting}[language=SQL,caption={Consulta 1.},label={lst:consulta1}]
SELECT pokemon.mote,
       especie.nombre_especie,
       especie.puntos_de_velocidad,
       entrenador.nombre_completo
FROM pokemon
JOIN especie ON pokemon.numero_de_pokedex = especie.numero_de_pokedex
JOIN entrenador ON pokemon.id_entrenador = entrenador.id
WHERE especie.tipo_principal = 'fuego';
\end{lstlisting}

\section{Fase IV. Ejecución de las consultas en Python}
\label{sec:fase4}

Desde Python se abre una conexión propia con el SGBD, se traen mediante
\textbf{SELECT * FROM tabla} únicamente las tablas necesarias y se combinan los datos
con código propio donde el cronómetro cubre todo ese recorrido.

\subsection{Conexión y medición de tiempos}

El código de conectividad y de medición es idéntico para MySQL y PostgreSQL. Lo único
que cambia entre ambos es la cadena de conexión.

\begin{lstlisting}[language=Python,caption={Comparación de las conexiones entre los SGBD.},label={lst:conexion-cambia}]
# MySQL
CONEXION = "mysql+pymysql://root:@localhost:3306/{base}"
# PostgreSQL
CONEXION = "postgresql+psycopg2://postgres:1234@localhost:5432/{base}"
\end{lstlisting}

El resto del código es común a ambos motores. Las funciones \texttt{consulta\_1} y
\texttt{consulta\_2} se muestran en la subsección siguiente.

\begin{lstlisting}[language=Python,caption={Conectividad y medición de tiempos, común a ambos motores.},label={lst:conexion}]
import os
import time
import pandas as pd
from sqlalchemy import create_engine

BASE = os.path.dirname(os.path.abspath(__file__))
TABLAS = ["especie", "entrenador", "tipo_de_objeto", "pokemon"]
BASES_DE_DATOS = ["pokemon_1k", "pokemon_10k", "pokemon_100k"]
CONEXION = "Depende del motor"

def traer_tablas(url, tablas=TABLAS):
    with create_engine(url).connect() as conexion:
        return {tabla: pd.read_sql(f"SELECT * FROM {tabla}", conexion)
                for tabla in tablas}


def cronometrar(funcion, argumento):
    inicio = time.perf_counter()
    resultado = funcion(argumento)
    return resultado, (time.perf_counter() - inicio) * 1000


medidas = []

for nombre_base in BASES_DE_DATOS:
    url = CONEXION.format(base=nombre_base)
    tablas, tiempo_traida = cronometrar(traer_tablas, url)
    resultado_1, tiempo_1 = cronometrar(consulta_1, url)
    resultado_2, tiempo_2 = cronometrar(consulta_2, url)

    filas_traidas = sum(len(tabla) for tabla in tablas.values())
    medidas.append([nombre_base, "traer tablas", tiempo_traida, filas_traidas])
    medidas.append([nombre_base, "consulta 1", tiempo_1, len(resultado_1)])
    medidas.append([nombre_base, "consulta 2", tiempo_2, len(resultado_2)])

tiempos = pd.DataFrame(medidas,
                       columns=["carga", "paso", "milisegundos", "filas"])
tiempos.to_csv(os.path.join(BASE, "tiempos.csv"), index=False)
\end{lstlisting}

\subsection{Solución de las consultas en Python}

Para las consultas en Python se empleó pandas, una de las librerías más usadas en
ciencia de datos para el procesamiento de información.

\begin{lstlisting}[language=Python,caption={Resolución de las consultas en Python.},label={lst:pyconsultas}]
def consulta_1(url):
    tablas = traer_tablas(url, ["pokemon", "especie", "entrenador"])
    con_especie = tablas["pokemon"].merge(tablas["especie"],
                                          on="numero_de_pokedex")
    con_entrenador = con_especie.merge(tablas["entrenador"],
                                       left_on="id_entrenador", right_on="id")
    de_fuego = con_entrenador[con_entrenador["tipo_principal"] == "fuego"]
    return de_fuego[["mote", "nombre_especie",
                     "puntos_de_velocidad", "nombre_completo"]]


def consulta_2(url):
    tablas = traer_tablas(url, ["pokemon", "entrenador", "tipo_de_objeto"])
    con_entrenador = tablas["pokemon"].merge(tablas["entrenador"],
                                             left_on="id_entrenador", right_on="id")
    con_objeto = con_entrenador.merge(tablas["tipo_de_objeto"],
                                      left_on="nombre_objeto", right_on="nombre")
    conteo = con_objeto.groupby(["nombre_completo", "categoria"]).size()
    conteo = conteo.reset_index(name="total_pokemon")
    return conteo.sort_values(["total_pokemon", "nombre_completo"],
                              ascending=[False, True])
\end{lstlisting}

De estos resultados se concluye que en la consulta 1 el mejor escenario fue PostgreSQL,
que ganó en las cargas de 10.000 y de 100.000 filas, y el peor la llamada de Python
desde MySQL.

En la consulta 2, en cambio, los dos motores quedaron prácticamente empatados, y el
mejor tiempo de la carga más grande no correspondió a ninguno de ellos sino a Python
desde PostgreSQL, con 998 ms. El peor escenario volvió a ser Python desde MySQL en las
tres cargas.

En la siguiente gráfica se muestran ambas consultas en escala logarítmica.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.85\linewidth]{consultas_sql.png}
  \caption{Tiempo de las consultas en SQL.}
  \label{fig:consultas-sql}
\end{figure}

Se observa que la diferencia entre motores es más marcada en la consulta 1, donde a
partir de las 10.000 filas la curva de PostgreSQL queda claramente por debajo de la de
MySQL, mientras que en la consulta 2 las dos curvas quedan casi superpuestas. Se aprecia
también que la consulta 2 es aproximadamente un orden de magnitud más costosa que la
consulta 1 en la carga de 100.000 filas, lo que se explica por el GROUP BY y el ORDER BY
que debe resolver.

Finalmente, en el siguiente gráfico se muestra la suma de los tiempos de ambas
consultas.

\begin{figure}[H]
  \centering
  \includegraphics[width=\linewidth]{general.png}
  \caption{Las dos consultas sumadas, por motor y por carga.}
  \label{fig:general}
\end{figure}

Se aprecia que con 1.000 filas el mejor es MySQL, con 8{,}4 ms contra 11 ms. Al crecer
la carga PostgreSQL pasa al frente, primero con holgura, 89 ms contra 113 ms, y después
por muy poco, 1{,}11 s contra 1{,}16 s. El peor resultado corresponde, en las tres
cargas, a la llamada de MySQL desde Python.

En conclusión, se pueden destacar los siguientes puntos.

\begin{itemize}[leftmargin=1.4em,itemsep=6pt,topsep=6pt]
  \item En el uso exclusivo de JOIN fue superior PostgreSQL, con más del doble de
        rapidez que MySQL en la carga de 100.000 filas.

  \item En las operaciones GROUP BY y ORDER BY (consulta 2) los dos motores quedaron parejos. Por lo tanto no se podría quien fue superior.

  \item Las llamadas desde Python junto con el uso de librerías especializadas no
        resultaron óptimas, y fue preferible ejecutar un script directamente dentro del
        SGBD. La única excepción fue la consulta 2 sobre 100.000 filas leída desde
        PostgreSQL, donde pandas quedó por delante del motor por un margen estrecho.

  \item Para la consulta de datos se mostró una ventaja general de los sistemas
        de gestión de bases de datos frente a los scripts de Python.

  \item En cuanto a la inserción, PostgreSQL fue significativamente mejor que MySQL en
        los tres tamaños de carga.
\end{itemize}
